# 最小完整改动：决策阶梯与永不裁剪

> 触发说法："怎么实现最小化" / "别过度设计" / "这代码能不能少写点" / "选型阶梯"。
> 提炼改编自 `DietrichGebert/ponytail`（MIT），融合本技能既有纪律。
> 核心一句话：**对方案懒，对改动不懒**——用最少的新代码完整解决任务，但该触及的调用方、测试、配置一处不落。

---

## 与 TDD 的关系（先说清，防止口径打架）

- 本文件的"最小"指的是**实现代码最少**，**不是测试最少**。
- **红在前铁律不变**：每个任务仍按 `tdd-playbook.md` 先写失败测试（红）再写实现（绿）。不采纳 ponytail 原文"trivial changes need none（一行改动不用测试）"的说法。
- 两者协同方式：**测试定义"完整"**，阶梯定义"最小"。测试本身就是"这个改动必须触及哪些行为"的清单。

---

## 动手前：先圈定范围

读任务 + 它要碰的代码，列出**这次改动必须触及的每一处**：

- 调用方（callers）——改了签名/返回值/行为，grep 所有调用点
- 测试与 fixtures——被你改动破坏的测试要一并修
- 配置、导出、文档

再确认：这个改动**会破坏什么**（会毁掉/暴露什么数据、哪些调用方会停摆）。这是范围；**额外功能不是范围**。

---

## 决策阶梯（六选一，从上往下取第一个可行的）

| 级 | 问自己 | 动作 |
|:--:|:---|:---|
| 1 | **它需要存在吗？** | 没人要求的功能、选项、灵活性 → 不做，并**用一句话说明跳过了什么** |
| 2 | **代码库里已经有了吗？**（helper/组件/服务/模式） | 用现成的，**按周围代码的用法用** |
| 3 | **标准库 / 平台能力有吗？** | 用标准库，除非项目有自己的封装（项目自有封装优先于原生能力） |
| 4 | **已装的依赖能做吗？** | 用它。**不为几行代码新加依赖** |
| 5 | **一行能写清吗？**（读者一眼能懂的那种） | 一行 |
| 6 | 以上都不行 | **能工作的最少代码** |

配合 `github-scouting.md` 使用：阶梯第 1–4 级查不到，再走 GitHub 查重确认"确实没有现成的"，才落第 6 级自研。

## 阶梯之外的硬规矩

- **删除优于新增**；保持代码库已有的分层、接口与约定。
- 不写没人要的：抽象、包装层、类型转换、选项、配置、样板、"以后再说"的代码。
- 数据保持平台已给的形态，不做无谓的转换。
- **最短的可工作 diff 获胜**——但"需要解码才能懂的一行"不算短。
- 修 bug：先 grep 每个调用方，**在共享代码里一次性修根因**，不在单个调用点打补丁。
- 搬移/合并的代码，原有的错误处理与校验**跟着走**。
- 同等大小两个方案，**选边界情况正确的那个**。
- 注释只写代码表达不了的 why，一行以内。

## Never cut 清单（为省事永不许砍的）

无论多想最小化，以下裁掉即违规：

1. **信任边界上的校验**（用户输入、外部数据入口）
2. **防止数据丢失的错误处理**
3. **安全**（鉴权、注入防护、密钥管理）
4. **可访问性**
5. **真实硬件所需的校准**
6. **用户明确要求的一切**

## shortcut 注释约定

带已知限制的捷径，必须留一行注释显式标记：

```
shortcut: <限制是什么>, <何时该升级>
```

被标记的 shortcut 是**决策**不是债务——但升级条件到了就必须处理。

## 收尾交代

每次交付末尾用一两行交代：

- **跳过了什么 / 没检查什么**
- **用户必须知道的风险**

> 示例：`跳过了并发场景测试（当前单进程使用）；风险：若未来多进程共用此文件需加锁。`

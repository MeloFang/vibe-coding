# 项目生命周期：从立项到交付的固定流程

> **这是本技能的主干道。** 五步闭环是其中的"编码内核"，本文档是包在外面的"项目外壳"。
> 用户说"开个新项目 / 从零做一个东西 / 我要立项"时，走这条流程，不要直接跳进编码。

## 为什么要走流程

从零做一个项目时，最容易出的错不是代码写错，而是**做着做着忘了要做什么**——目标漂移、上下文丢失、进度不明、接手的人看不懂。

固定流程的价值就是：**每个阶段都有一份落盘产物，任何人（包括下次的你）都能从文件判断现在在哪。**

## 六个阶段

```
① 立项与产品文档  →  ② 固定上下文  →  ③ 规划
                                          ↓
                              ⑥ 续接文档（全程维护）
                                          ↓
                       ④ 实现  →  ⑤ 验证  →  ⑥ 续接文档（更新）
```

| 阶段 | 产物 | 谁写 | 什么时候做 |
|:---|:---|:---|:---|
| ① 立项与产品文档 | `PRODUCT.md` | 你 + Agent 协作 | 动手前，**第一件事** |
| ② 固定上下文 | `AGENTS.md` + `GLOSSARY.md` + `docs/adr/` | Agent | 立项后立刻 |
| ③ 规划 | `PLAN.md` | Agent | 上下文固定后 |
| ④ 实现 | 代码 + 测试 | Agent | 规划后，每步都更新状态 |
| ⑤ 验证 | 验收记录 | Agent + 人审 | 每个功能完成时 |
| ⑥ 续接文档 | `HANDOFF.md`（**全程维护**） | Agent | 每个阶段结束都更新 |

**关键**：`HANDOFF.md` 不是最后才写的，是**从① 开始就建起来、每个阶段都更新**的活文档。见 `project-docs.md`。

---

## ① 立项与产品文档

**这是最容易被跳过、但最不能跳的一步。**

跳过它 = 需求只存在于聊天记录里 = 三天后你自己也想不起来当初为什么要做。

产品文档不是产品经理的 PPT，是**决策锚点**。它要回答：

- 这个程序**解决什么问题**？（不是"我要做个 XX"，而是"谁、遇到什么痛点、现在怎么办"）
- **目标用户**是谁？怎么用？
- **成功标准**是什么？（怎么算做成了）
- **范围边界**：明确不做什么。
- **约束**：时间、技术、依赖、数据。

模板见 `project-docs.md` 的「产品文档」段。**由 Agent 起草、你审改**——不要 Agent 自己拍板产品定义，那必须你来定。

### 阶段出口

- [ ] `PRODUCT.md` 已落盘
- [ ] 成功标准是可验证的（不是"好用"，而是"1000 条记录处理 < 3 秒"）
- [ ] 范围边界写清了"不做什么"
- [ ] 你（用户）已确认——**这一步没确认，不许进下一阶段**

---

## ② 固定上下文

把项目变成"AI 可读的项目"。三份文件，各司其职：

| 文件 | 回答什么问题 | 什么时候写 |
|:---|:---|:---|
| `AGENTS.md` | 这个项目怎么构建、怎么测、代码什么风格 | 立项后立刻，一次写完主体 |
| `GLOSSARY.md` | 这个项目的黑话分别指什么 | 边做边补，遇到新术语就加 |
| `docs/adr/` | 为什么这么做（反直觉的决策） | 遇到"难以逆转+反直觉+真权衡"的决策时 |

模板见 `AGENTS-template.md` 和 `CONTEXT-template.md`。

### 为什么不能靠聊天记录

- 上下文窗口有限，聊久了前面就丢了。
- 每个 Agent 会话独立，上一个会话的结论下一个会话看不到。
- 三个月后你自己也翻不动聊天记录。

**文档是给未来的"你"和"接手的人"看的**，不是给当前会话看的。

### 阶段出口

- [ ] `AGENTS.md` 已落盘，含可执行的构建/测试命令
- [ ] 术语表已建（至少覆盖核心名词）
- [ ] 任何 Agent 读完这两份文件就能开始干活，不需要问基础问题

---

## ③ 规划

把产品文档拆成**可执行、可验证的步骤**。

原则：
- **每步带验收信号**——做完怎么知道成了。
- **一次只做一步**，不要并行铺开。
- **垂直切片**——每步都是一条能跑通的细长路径（一个测试 → 一个实现），不是"先写完所有模型再写所有视图"。
- **只写指令不写实现**——规划文档里不该出现大段代码。

模板见 `project-docs.md` 的「实施计划」段。

### 阶段出口

- [ ] `PLAN.md` 已落盘
- [ ] 每一步都有明确验收标准
- [ ] 每步粒度适中（一半天到一天，不是"实现全部功能"）
- [ ] 步骤之间有顺序依赖说明

---

## ④ 实现

进入五步闭环（见 SKILL.md 正文）：对齐 → 固定上下文（增量）→ 规划（增量）→ 分步实现 → 复盘。

**这一步的核心纪律**：
- **红在前**：先写失败测试再写实现。
- **一次一片**：一个接缝、一个测试、一次最小实现。
- **每步做完立刻更新 `PLAN.md` 状态和 `HANDOFF.md` 进度**——不要攒到最后。

### 阶段出口（每个功能）

- [ ] 测试通过（红→绿循环走完）
- [ ] `PLAN.md` 里对应步骤标记为完成
- [ ] `HANDOFF.md` 进度已更新
- [ ] **走 `finishing-branch.md` 流程决定去向**（新增 —— 不许直接开始下一个功能）

---

## ⑤ 验证

**不是"跑一遍没报错"，是"对着成功标准逐条核对"。**

分三层：

| 层 | 谁做 | 怎么验 |
|:---|:---|:---|
| **功能验收** | 人审| 对着 `PRODUCT.md` 的成功标准逐条走，Agent 出检查清单 |
| **技术验证** | Agent | 测试全绿、构建通过、关键路径性能达标 |
| **回归验证** | Agent | 改动没破坏已有功能（跑全量测试） |

**Agent 可以跑测试，但不能自己宣布"验收通过"**——最终判断必须人来下。

### 阶段出口

- [ ] `PRODUCT.md` 的每条成功标准都核对了
- [ ] 全量测试绿
- [ ] 已知限制和未完成项写进 `HANDOFF.md`

---

## ⑥ 续接文档

**从① 开始就建，每个阶段都更新。** 这是本流程的"元文档"——它同时装着三样东西：

1. **这个程序是什么**（讲给完全不了解的人听）
2. **做到哪一步了**（讲给要接手的人听）
3. **怎么接着做**（讲给下一个 Agent 或未来的你听）

模板见 `project-docs.md` 的「续接文档」段。维护规则见 `handoff.md`。

---

## 每阶段新会话（借 humanlayer/skills·rpi）

`humanlayer/skills` 的 `rpi`（Research → Plan → Implement）有一条硬设定：**每个阶段默认在独立会话里跑**——"Users run each phase in a separate context window by default."，阶段之间只靠 `.agents/artifacts/<task-slug>/` 下的文档交接，用 `NN-` 前缀编号，文档 frontmatter 带 `repos: [{identifier, sha}]` 记录"这份文档针对哪个仓库的哪个 commit"。

### 它和本流程是什么关系

**同一套"文档即上下文"思路的两个强度档，不冲突：**

| | 本流程（默认） | rpi |
|:---|:---|:---|
| 上下文载体 | 仓库里的 `PRODUCT/AGENTS/PLAN/HANDOFF` | `.agents/artifacts/<slug>/NN-*.md` |
| 会话 | 同一会话可连跑多阶段 | **每阶段一个新会话** |
| 阶段数 | 六阶段（含立项/验证/续接） | research / prd / tdd / outline / implement |
| 产物归属 | 提交进仓库 | 作者建议**不提交** |

本流程之所以不强制每阶段新会话，是因为它靠**落盘文档**续接——文档够了，同会话跑完反而更快、更少丢上下文。

**但一旦出现下面任一信号，就该切成"每阶段新会话"**：

- 会话已经很长、开始压缩 / 你发现 Agent 在"忘记前面说过什么"
- 这个阶段要读大量代码或文档（research 型），读进来只为产出一份结论
- 阶段之间**结论会污染判断**（例如：先做了大量实现调研，再回去做需求取舍，容易偏向已调研的方案）
- 任务跨天、跨人

### 切法（照抄 rpi 的可移植部分）

1. **建任务目录**：`.agents/artifacts/<task-slug>/`（分支名或短 kebab-case slug 命名）。可加进 `.gitignore`——**它是工作台，不是交付物**。
2. **每阶段只喂该阶段需要的文档**：不要让新会话把全部历史都读一遍，只读上一阶段的结论 + 必要代码。
3. **阶段末写 handoff**：本阶段结论 + 未决项 + 下一步命令，供下一阶段会话开篇读。
4. **文档 frontmatter 记 `repos: [{identifier, sha}]`** —— 这条值得借：它把"这份结论是针对哪个代码状态得出的"钉死了，相当于本技能 ADR/证据等级的轻量版。**结论回流到 `PLAN.md` / `HANDOFF.md` 时把这个 sha 带上。**

### 取舍：rpi 说"artifacts 不提交"，本技能不照抄

rpi 作者建议不提交 `.agents/artifacts/`——因为它是一次性工作台。

本技能的口径是：**`PRODUCT.md` / `PLAN.md` / `HANDOFF.md` / `AGENTS.md` / `GLOSSARY.md` 必须提交**，它们是"这程序是什么、到哪一步、怎么接手"的唯一记录；只有**单次临时交接**不落仓库（见 `handoff.md`）。

所以兼容做法是：

> `.agents/artifacts/` 当**草稿区**（可 gitignore），但**每个阶段定稿的结论必须回流**到 `PLAN.md` / `HANDOFF.md`（必要时进 ADR）。
> 别让结论只活在不提交的工作台里——那正是"做着做着忘了要做什么"的复发点。

## 什么时候可以跳过流程

不是所有任务都值得走全流程。按规模选：

| 规模 | 走哪些 | 产物 |
|:---|:---|:---|
| **一次性脚本 / 小工具**（<半天） | ②③④，①②③ 口头确认即可 | 代码 + 测试 |
| **单个功能**（1–3 天） | ②③④⑤ + 简版 `HANDOFF.md` | AGENTS + PLAN + 进度 |
| **完整项目**（>1 周） | 全六阶段 | PRODUCT + AGENTS + GLOSSARY + ADR + PLAN + HANDOFF |

**判断标准**：这事会不会跨越会话？会不会有别人接手？会 → 走全流程。不会 → 走轻量版。

**但产品文档（①）永远值得写**，哪怕三行字。它是"为什么要做这件事"的唯一记录。

# 接收审查反馈：如何响应审查意见

> 触发说法："审查出了问题" / "有 feedback" / "审查者提了问题" / "怎么响应审查"

**铁律**：审查反馈不是"批评"，是**帮助发现盲点**。响应流程化，不许情绪化。

---

## 响应流程

```
① 分类问题  →  ② 修复计划  →  ③ 逐条修复  →  ④ 验证通过
```

| 步骤 | 产物 | 出口条件 |
|:---|:---|:---|
| ① **分类问题** | 问题清单（严重/一般） | 每条问题已分类 |
| ② **修复计划** | 修复排期 | 每条问题有负责人 + 时间 |
| ③ **逐条修复** | 修复提交 | 严重问题已修复 |
| ④ **验证通过** | 验证记录 | 审查者确认通过 |

---

## 步骤①：分类问题

**目标**：把审查报告里的问题分类，明确哪些必须修、哪些可排期。

### 问题分类

| 类别 | 含义 | 响应时间 |
|------|------|----------|
| **严重问题** | blocking，必须修复后才能继续 | 立即修复 |
| **一般问题** | non-blocking，可排期修复 | 排期修复 |
| **误解** | 审查者理解有误 | 澄清说明 |
| **技术债务** | 不紧急但应改进 | 记录到 HANDOFF.md |

### 输出格式

```markdown
## 问题分类

**审查报告**: <链接>

**严重问题**（立即修复）:
1. 测试缺失（密码为空边界）
2. 硬编码（API 密钥写死）

**一般问题**（排期修复）:
1. 命名不一致（`user_id` vs `uid`）
2. 注释缺失（复杂逻辑无注释）

**误解**（需澄清）:
1. 无

**技术债务**（记录 HANDOFF.md）:
1. 可优化：缓存层可提升性能 20%
```

---

## 步骤②：修复计划

**目标**：每条问题有负责人 + 修复时间，不许"看着办"。

### 修复排期

| 问题 | 负责人 | 修复时间 | 状态 |
|------|--------|----------|------|
| 测试缺失 | @作者 | 立即 | 进行中 |
| 硬编码 | @作者 | 立即 | 进行中 |
| 命名不一致 | @作者 | 明天 | 待修复 |
| 注释缺失 | @作者 | 本周内 | 待修复 |

### 输出格式

```markdown
## 修复计划

**严重问题**（今天内修复）:
1. 测试缺失 → @作者，20:30 前
2. 硬编码 → @作者，20:30 前

**一般问题**（排期）:
1. 命名不一致 → @作者，明天（2026-10-17）
2. 注释缺失 → @作者，本周内（2026-10-20 前）

**技术债务**（HANDOFF.md 记录）:
1. 缓存层优化 → 记录到 HANDOFF.md，排期 Q1
```

---

## 步骤③：逐条修复

**目标**：按修复计划逐条修复，每修复一条更新状态。

### 修复纪律

- **严重问题优先**：先修复 blocking 问题
- **小步提交**：每修复一条一个提交
- **提交信息清晰**：说明修复什么问题

### 提交信息格式

```
<type>: <description>

修复审查问题：<问题描述>

审查报告：<链接>
```

**示例**：
```
test: 添加密码为空边界测试

修复审查问题：测试缺失（密码为空边界）

审查报告：link-to-review-report
```

### 输出格式

```markdown
## 修复进度

**严重问题**:
- [x] 测试缺失 → 已修复（abc123）
- [x] 硬编码 → 已修复（def456）

**一般问题**:
- [ ] 命名不一致 → 待修复（明天）
- [ ] 注释缺失 → 待修复（本周内）

**技术债务**:
- [x] 缓存层优化 → 已记录 HANDOFF.md
```

---

## 步骤④：验证通过

**目标**：审查者确认严重问题已修复，宣布通过。

### 验证清单

- [ ] 严重问题已修复
- [ ] 修复提交信息清晰
- [ ] 重新审查通过
- [ ] PLAN.md 状态更新
- [ ] HANDOFF.md 已更新

### 输出格式

```markdown
## 验证通过

**审查者**: @<审查者>

**确认**:
- [x] 严重问题已修复
- [x] 修复提交信息清晰
- [x] 重新审查通过

**PLAN.md 状态**: ✅ 完成

**HANDOFF.md**: 已更新（技术债务记录）

**时间**: 2026-10-16 20:30
```

## 响应审查的最佳实践

### ✅ 好的响应

```
收到审查反馈，感谢指出问题！

**严重问题**（立即修复）:
1. 测试缺失 → 正在修复，预计 20:30 完成
2. 硬编码 → 正在修复，预计 20:30 完成

**一般问题**（排期）:
1. 命名不一致 → 明天修复
2. 注释缺失 → 本周内修复

修复完成后会重新提交审查，感谢！
```

### ❌ 坏的响应

```
这不算问题吧？
我觉得这样写挺好的。
你不懂我的设计。
```

**问题**：情绪化，不专业，不解决问题。

---

## 澄清误解

**当审查者理解有误时**：

### 澄清流程

```
① 感谢指出  →  ② 解释设计意图  →  ③ 确认是否需改进文档
```

**示例**：
```
感谢指出这个问题！

这里的设计意图是 XXX（解释原因）。不过确实容易让人误解，我会：
1. 添加注释说明设计意图
2. 更新 GLOSSARY.md 记录这个术语

这样可以吗？
```

**关键**：不争论，解释意图 + 改进文档。

## 技术债务管理

**一般问题/技术债务**：记录到 HANDOFF.md，排期修复。

### HANDOFF.md 记录格式

```markdown
## 技术债务（2026-10-16 审查）

**来源**: 任务间审查

**债务**:
1. 命名不一致（`user_id` vs `uid`）→ 排期 2026-10-17
2. 注释缺失（复杂逻辑）→ 排期 2026-10-20
3. 缓存层优化（可提升性能 20%）→ 排期 Q1 2027

**负责人**: @作者

**审查者**: @审查者
```

## 与其他流程的衔接

- **分类问题** → 走 `diagnosing-session.md`（如是会话问题）
- **修复复杂问题** → 走 `tdd-playbook.md`（红→绿循环）
- **发现架构问题** → 走 `architecture-review.md` 体检
- **更新 HANDOFF.md** → 走 `handoff.md` 格式
- **验证通过** → 走 `finishing-branch.md` 收尾

---

## 常见错误

| 错误 | 症状 | 修复 |
|------|------|------|
| **情绪化响应** | "这不算问题" / "你不懂" | 专业化，感谢 + 分类 + 修复 |
| **不分类** | 所有问题混在一起 | 严重/一般/误解/债务分类 |
| **无排期** | "看着办" / "以后修" | 明确负责人 + 修复时间 |
| **修复不提交** | 口头说修了，无提交记录 | 小步提交，信息清晰 |
| **不验证** | 修复后不重新审查 | 审查者确认通过 |

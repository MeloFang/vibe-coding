# 对齐深挖方法论（提炼自 mattpocock 的 grilling / grill-me / grill-with-docs）

> 对齐不是"问几个问题就开干"。它是一棵**设计树**，一轮一轮把树上的决策全部落定。
> 本文件是 `vibe-coding` 五步闭环里第① 步的展开。

## 核心模型：设计树（design tree）

把要做的决策画成一棵树：每个决策下面挂着它依赖的子决策。

- **前沿（frontier）** = 所有前置决策已经落定、**现在**就能问的问题——不问就等于在猜那些还没听到答案的事。
- 一轮只问整个前沿，不掺带依赖后面问题的东西。
- 问完一轮，用户的答案会**重塑树**：定下来的决策把前沿往外推，解锁之前被它挡住的子问题。重新计算前沿，问下一轮。
- **完成条件**：前沿清空——设计树每条分支都走过，没有东西被默默地假设掉。
- **在用户确认达成共识之前，不要动手实现。**

## 一轮的格式

```
❓ **Q1** — **<问题标题>**: <问题正文，可多段，可带选项>

➡️ <我的推荐答案>

---

❓ **Q2** — **<问题标题>**: <问题正文，可多段，可带选项>

➡️ <我的推荐答案>
```

**关键技巧：每个问题都要写成"回答 yes 就等于采纳我的推荐"。** 这样用户回一个"是"就能推进，不用反复解释。

## 事实 vs 决策：分工要清楚

- **找事实是你的活**，永远不是用户的。需要环境事实（文件系统、工具、代码现状）时，派个子 Agent 去查，别问用户。
- **决策是用户的活**，把每个决策摆给他，然后等。

不要因为一个探索还没跑完就整体阻塞：正在跑的探索属于"未定的前置"，只有它下游的问题要等，**前沿里其他问题现在就问**。

## 最小起步清单

前沿没算出来之前，先用这几条开盘（也适合轻量任务直接用完）：

- 这次的**目标**是什么？**非目标**（明确不做）是什么？
- 技术栈 / 约束 / 已有代码在哪？
- **验收标准**是什么（怎么算"做对了"）？
- 风险点 / 不确定项有哪些？

## 边烤问边沉淀（grill-with-docs 的那一半）

烤问过程中一旦有结论**当场落盘**，不要攒到最后一起写：

- **术语**定下来了 → 更新 `GLOSSARY.md`（若项目用旧约定则是 `CONTEXT.md`）。
- **决策**值不值得记 → 考虑写 ADR。

### ADR 的门槛（三条全中才写）

1. **难以逆转**：以后改主意的代价可观。
2. **没有上下文会让人困惑**：未来读者会问"为什么这么做？"。
3. **源于真实权衡**：确实存在其他选项，你出于具体理由选了这个。

缺任何一条就别写 ADR。"现在不划算"这种临时理由、自明的理由，都不值得占一个 ADR。

### 领域模型维护（domain-modeling 的内核）

- **对着术语表抬杠**：用户用的词和 `GLOSSARY.md` 里的定义冲突，立刻点出来——"你的术语表把'取消'定义为 X，但你现在说的像是 Y，哪个对？"
- **把模糊词变精确**：用户说含糊或过载的词，给出精确的规范词——"你说的'账号'，是指 Customer 还是 User？这是两回事。"
- **拿具体场景压测**：讨论领域关系时，用具体场景追问，**自己编边界场景**，逼用户把概念边界说清。
- **跟代码对照**：用户陈述某个机制时，去代码里核对。矛盾就摆出来——"你的代码是取消整个 Order，但你刚说可以部分取消，哪个对？"

**术语表里不许有实现细节**。它是术语表，不是规格说明书，不是草稿纸，不是实现决策的储藏室。

# 深模块设计词汇（提炼自 mattpocock 的 codebase-design）

> `vibe-coding` 四大纪律里"架构卫生"这一条的方法论底座。
> **这些词必须原样使用**——统一术语本身就是这套方法论的价值。

## 词汇表

| 词 | 定义 | 别用 |
|:---|:---|:---|
| **Module** 模块 | 任何有接口和实现的东西。**刻意与规模无关**：一个函数、一个类、一个包、一个跨层切片 | unit、component、service、组件 |
| **Interface** 接口 | 调用者必须知道才能正确使用它的**全部**：类型签名，外加不变式、顺序约束、错误模式、必需配置、性能特征 | API、signature（都太窄，只指类型层表面） |
| **Implementation** 实现 | 模块里面的代码本体。**区别于 Adapter**：一个模块可以是大实现配小适配器（Postgres 仓储），也可以是小实现配大适配器（内存假实现） | —— |
| **Depth** 深度 | 接口处的杠杆。调用者（或测试）每学一单位接口能驱动多少行为。**深** = 小接口藏大行为；**浅** = 接口复杂度≈实现复杂度 | —— |
| **Seam** 接缝 | 不用改那处代码就能改变行为的地方；模块接口所在的**位置**。接缝放哪儿本身是个设计决定，跟接缝后面放什么相互独立 | boundary（与 DDD 有界上下文混淆） |
| **Adapter** 适配器 | 在接缝上满足某个接口的具体东西。描述**角色**（填哪个槽位），不是**实质**（里面装什么） | —— |
| **Leverage** 杠杆 | 调用者从深度里拿到的好处。每单位接口学到的能力更多；一份实现被 N 个调用点、M 个测试复用 | —— |
| **Locality** 局部性 | 维护者从深度里拿到的好处。改动、bug、知识和验证集中在一处而非散在各处。改一次，处处生效 | —— |

## 深 vs 浅

```
深模块 = 小接口 + 厚实现              浅模块 = 大接口 + 薄实现（要避免）
┌─────────────────────┐              ┌─────────────────────────────────┐
│    Small Interface  │ 少方法       │       Large Interface            │ 多方法
├─────────────────────┤              ├─────────────────────────────────┤
││                                 │  Thin Implementation            │ 只是转发
│  Deep Implementation │ 藏复杂逻辑  │                                 │
└─────────────────────┘              └─────────────────────────────────┘
```

设计接口时问自己：**能减少方法数量吗？能简化参数吗？能把更多复杂藏进去吗？**

## 四条原则

1. **深度是接口的属性，不是实现的属性。** 深模块内部可以由很多小而可 mock、可替换的部件组成——它们只是不属于接口。模块可以有**内部接缝**（实现私有，给自己的测试用），以及接口处的**外部接缝**。
2. **删除测试。** 想象删掉这个模块：复杂度消失 → 它只是个转发壳；复杂度在 N 个调用方重新出现 → 它在挣自己的饭。
3. **接口就是测试面。** 调用者和测试跨的是同一个接缝。如果你想**越过**接口去测，说明这个模块形状不对。
4. **一个 adapter 意味着假想的接缝，两个 adapter 才是真接缝。** 别引入一个没有东西真正在其上变化的接缝。

## 为可测试性设计

### 1. 接受依赖，不要创造依赖

```python
# 好：依赖从外面来，可注入
def process_order(order, payment_gateway):
    ...

# 差：内部自己造，没法换也没法假
def process_order(order):
    gateway = new StripeGateway()
    ...
```

### 2. 返回结果，不产生副作用

```python
# 好：返回结果，可断言
def calculate_discount(cart) -> Discount:
    ...

# 差：改外部状态，测不出来
def apply_discount(cart) -> None:
    cart.total -= discount
    ...
```

### 3. 表面面积小

方法少 → 要写的测试少。参数少 → 测试装配简单。

## 术语间关系

- 一个 **Module** 恰有一个 **Interface**（它呈现给调用者和测试的表面）。
- **Depth** 是 **Module** 的属性，相对其 **Interface** 度量。
- **Seam** 是 **Module** 的 **Interface** 所在的位置。
- **Adapter** 坐在 **Seam** 上，满足 **Interface**。
- **Depth** 为调用者产生 **Leverage**，为维护者产生 **Locality**。

## 被拒绝的表述

- ❌ **"深度 = 实现行数 / 接口行数"**（Ousterhout 的比率法）——那会奖励往实现里灌水。用"深度即杠杆"。
- ❌ **"Interface" 当成 TypeScript 的 `interface` 关键字或类的公开方法**——太窄。这里 interface 指调用者必须知道的**每一件事**，含不变式和顺序约束。
- ❌ **"Boundary"**——与 DDD 有界上下文混淆。说 **seam** 或 **interface**。

## 怎么用这套词审查自己的代码

- **浅模块识别**：接口方法数量和实现复杂度旗鼓相当？删掉它试试——复杂度是消失还是平移？
- **抽出纯函数只为可测性**是典型信号：真正的 bug 往往不在纯函数里，而在**它怎么被调用**（缺 locality）。
- **tight coupling跨接缝泄漏**：改一处要动好几个模块，说明接缝放错了。
- **没测试 / 难以通过当前接口测试**：模块形状可能不对，先考虑深模块化而不是加内部测试钩子。

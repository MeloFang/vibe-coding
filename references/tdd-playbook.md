# TDD 完整方法论（提炼自 mattpocock 的 tdd 技能）

> 这是 `vibe-coding` 五步闭环里"反馈环铁律"的展开。每一节在**每轮红绿循环前后都适用**，不是循环结束后才翻的参考。

## 好测试的标准

测试通过**公共接口**验证行为，不验证实现细节。代码可以整个换掉，测试不该跟着碎。

一个好测试读起来像规格说明：

> "用户能带着有效购物车结账"

这句话本身就说明存在哪项能力，而且它能在重构中存活，因为它不关心内部结构。

**读测试名就知道有什么能力**，是判断测试质量的最快方法。

## 接缝（seam）：测试放在哪

**接缝**是你观察行为而不伸手进内部的**公共边界**。测试住在接缝上，绝不测内部。

### 只在预先约定的接缝上测

写任何测试之前，先把"要在哪些接缝上测"写下来，跟用户确认。**没确认过的接缝不写测试。**

你不可能测所有东西，所以**事先约定接缝，是让测试力量落在关键路径和复杂逻辑上、而不是落在每个边角case上的办法**。

每个候选接缝给一行说明：它能抓住什么、漏掉什么。

## 三个反模式

### 1. 实现耦合（Implementation-coupled）

mock 内部协作者、测私有方法、或者绕过接口从旁路查询（比如直接查数据库而不是走接口）。

**识别信号**：你重构了、但行为没变，测试却挂了。

### 2. 同义反复（Tautological）

断言用代码同样的算法把期望值算出来：

```python
assert add(a, b) == a + b          # 同义反复
assert snapshot == hand_made_snapshot  # 同义反复
assert CONST == CONST                  # 同义反复
```

这类测试**按构造就成立**，永远不可能和代码分歧，等于没测。

**期望值必须来自独立的真相源**：已知正确的字面量、算出来的例子、规格说明。

### 3. 水平切片（Horizontal slicing）

先把所有测试写完，再写所有实现。

问题：你测的是**想象出来的行为**，测的是东西的**形状**而不是用户可感知的行为；测试对真实变化不敏感；而且你在还没理解实现之前就把测试结构提交了。

**正确做法：垂直切片。** 一个测试 → 一个实现 → 重复。每个测试都是一发**曳光弹（tracer bullet）**，能对上一轮学到的东西做出反应。

## 循环规则

- **先红后绿。** 先写失败的测试，再只写刚好让它通过的代码。不预支未来的测试，不加投机性功能。
- **一次一片。** 一个接缝、一个测试、一次最小实现。
- **重构不在这轮循环里。** 重构属于审查阶段（见复盘），不属于红绿实现循环。

## 强制执行机制（P3 优先级）

> 提炼自 Superpowers 的 `test-driven-development` 技能。

### 删除违规代码

**铁律**：发现代码 written before tests（测试前写的代码）→ **删除**，重新写测试 → 再写实现。

**识别信号**：
- 提交历史里实现提交在测试提交之前
- 自审时发现"先写了实现，想着回头补测试"
- 审查者指出"这个测试像事后补的"

**删除流程**：
```
发现违规 → 删除实现 → 写测试（红） → 重写实现（绿） → 提交
```

**输出格式**：
```markdown
## TDD 违规修复

**违规代码**: `src/auth.py` 的 `login()` 函数

**删除提交**: `abc123` - revert: feat: 实现登录验证

**测试提交**: `def456` - test: 添加登录验证测试（红）

**实现提交**: `ghi789` - feat: 实现登录验证（绿）

**教训**: 不许先写实现再补测试
```

---

### 审查检查点

**铁律**：每个任务完成后走 `requesting-code-review.md` 时，**必须检查 TDD 遵守情况**。

**检查清单**：
- [ ] 提交历史里测试提交在实现提交之前
- [ ] 每个测试都是红→绿循环（不是事后补的）
- [ ] 期望值来自独立真相源（不是同义反复）
- [ ] 测试在接缝上（不是测内部细节）

**输出格式**：
```markdown
## TDD 遵守检查

**任务**: <任务名称>

**检查结果**:
- [x] 测试提交在实现提交之前
- [x] 红→绿循环完整
- [x] 期望值来自独立真相源
- [x] 测试在接缝上

**违规**: 无
```

### 技术债务跟踪

**铁律**：发现 TDD 违规但不紧急修复 → **记录到 HANDOFF.md**，排期重构。

**记录格式**：
```markdown
## TDD 技术债务（2026-10-16）

**来源**: 任务间审查

**违规**:
1. `src/auth.py` 的 `login()` 函数 → 测试后补（排期 2026-10-17）
2. `src/utils.py` 的 `validate()` 函数 → 同义反复测试（排期 2026-10-18）

**负责人**: @作者

**审查者**: @审查者
```

**排期原则**：
- 核心功能 → 24 小时内重构
- 边缘功能 → 本周内重构
- 实验性功能 → 观察后决定

---

### 与审查流程的衔接

- **发现违规** → 走 `requesting-code-review.md`（严重问题 blocking）
- **删除实现** → 走五步闭环（红→绿循环）
- **排期重构** → 走 `receiving-code-review.md`（技术债务记录）
- **更新 HANDOFF.md** → 走 `handoff.md` 格式

---

### 常见错误

| 错误 | 症状 | 修复 |
|------|------|------|
| **不删除违规** | "回头补测试" | 强制删除，重新红→绿 |
| **审查不检查** | 违规没发现 | 审查清单增加 TDD 检查 |
| **债务不记录** | 违规堆积 | HANDOFF.md 强制记录 |
| **排期不明确** | "以后重构" | 明确 24 小时/本周内 |

---

> **注意**：TDD 强制不是"形式主义"，是**确保测试不是事后补的**。事后补的测试按构造就成立，永远测不出东西。

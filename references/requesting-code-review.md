# 任务间审查：每个任务完成后审查

> 触发说法："审查一下这个任务" / "检查实现质量" / "看看有没有问题" / "任务完成了，审查"

**铁律**：每个任务完成后**必须**走审查流程，**严重问题 blocking**（不许继续下一个任务）。

---

## 审查时机

```
任务完成 → 审查 → 修复（如有）→ 下一个任务
```

| 时机 | 说明 |
|------|------|
| **每个任务完成后** | 不许攒到最后一起审查 |
| **下一个任务开始前** | 确保问题不传递 |
| **严重问题 blocking** | 不许继续，先修复 |

---

## 审查检查清单

### 严重问题（blocking，必须修复）

- [ ] **功能不符合 PLAN.md / Dispatch 包**（做错了方向）
- [ ] **测试缺失**（没有测试或测试不覆盖验收标准）
- [ ] **硬编码**（配置/路径/密钥写死在代码里）
- [ ] **安全漏洞**（SQL 注入/XSS/路径遍历等）
- [ ] **性能回退**（关键路径性能下降>10%）
- [ ] **命名与 GLOSSARY.md 冲突**（术语不一致）

**处理**：发现任一 → **blocking**，必须修复后重新审查才能继续。

### 一般问题（non-blocking，可排期修复）

- [ ] **命名不一致**（同一概念用了不同名字）
- [ ] **代码重复**（DRY 违反，但不影响功能）
- [ ] **注释缺失**（复杂逻辑无注释）
- [ ] **格式问题**（缩进/空行/换行符）
- [ ] **提交信息不清晰**（commit message 模糊）

**处理**：记录到 HANDOFF.md，排期修复（不影响继续）。

---

## 审查流程

```
① 自审  →  ② 提交审查  →  ③ 审查者审查  →  ④ 修复（如有）→  ⑤ 通过
```

| 步骤 | 产物 | 出口条件 |
|:---|:---|:---|
| ① **自审** | 自审报告 | 作者已按清单检查 |
| ② **提交审查** | 审查请求 | 审查者已收到 |
| ③ **审查者审查** | 审查报告 | 严重问题已识别 |
| ④ **修复** | 修复提交 | 严重问题已修复 |
| ⑤ **通过** | 通过记录 | PLAN.md 状态更新 |

---

## 步骤①：自审

**作者职责**：在提交审查前，先自己按清单检查一遍。

**输出格式**：
```markdown
## 自审报告

**任务**: <任务名称>

**自审结果**:
- [x] 功能符合 PLAN.md / Dispatch 包
- [x] 测试覆盖验收标准
- [x] 无硬编码
- [x] 无安全漏洞
- [x] 性能无回退
- [x] 命名符合 GLOSSARY.md

**已知问题**:
- <如有一般问题，提前记录>

**提交审查**: 准备提交给 <审查者>
```

---

## 步骤②：提交审查

**提交方式**：
- 会话内：直接@审查者，粘贴审查请求
- 远端：GitHub PR / GitLab MR
- 本地：更新 PLAN.md 状态为"待审查"

**输出格式**：
```markdown
## 审查请求

**任务**: <任务名称>

**自审**: [x] 通过

**变更**:
- 文件 1: `src/auth.py`（新增登录验证）
- 文件 2: `tests/test_auth.py`（新增测试）

**审查者**: @<审查者>

**截止时间**: <可选，如"30 分钟内">
```

---

## 步骤③：审查者审查

**审查者职责**：
- 读代码 + 测试（**不只读 diff**——还要读被改函数的调用方、它调用的函数、相关测试）
- 按清单检查
- 输出审查报告

### 审查三条硬规矩（改编自 ponytail-review）

1. **没有具体场景，就不算发现。** 每条发现必须给出"这个输入/这种情况下会导致这个错误结果"。举不出场景的泛泛之谈（"建议考虑""可能有风险"）一律不写。
2. **报告前复查一遍**：引用的调用方真的存在吗？那个值真的可能为空吗？那段代码真的没人用吗？
3. **提出能工作的最小修法**，优先删代码的修法；不加问题不需要的层、框架、配置。没有风格品味之争，没有"考虑一下"。

### 审查报告格式（三组 + 全局编号 + 四段式）

发现分三组（空组跳过），**编号跨组连续**（用户可以直接说"修 2 和 5"）：

```markdown
## 审查报告

**任务**: <任务名称>
**审查者**: @<审查者>

**这个改动做了什么**: <两三句话，给没看过这段代码的人>

### Must fix（必须修：bug / 安全 / 数据丢失 / 在预期负载下会崩）

1. **<一句话标题>**（`文件路径:行号`）
   - **这是什么**: <这个代码在做什么，一两句>
   - **问题**: <具体场景——什么输入/什么情况下出现什么错误结果>
   - **修法**: <最小修法，具体到改哪几行>
   - **不修的后果**: <跳过它会发生什么>

### Should fix（该修：风险代码没测试 / 真实重复 / 一个函数混几件事 / 不该存在的代码）

2. **…**（同上四段式）

### Nice to have（可改：小提速、更短写法）

3. **…**（同上四段式）

**结论**: `Verdict: Ship.` 或 `Verdict: 先修 1 和 2。`
**可精简**: `Lean: -<N> 行可省。`（有精简类发现时）
**未检查**: <有该查没查到的，一行说明；没有就省略>
```

- **结论行必写**：`Ship`（可直接合）或 `先修 N 和 N`（指名编号）。不许写"总体不错，建议关注"这种没有行动性的话。
- 四段式里**"不修的后果"最不能省**——它决定这条算 Must 还是 Should。

---

## 步骤④：修复

**作者职责**：
- 逐条修复严重问题
- 更新提交
- 重新提交审查

**输出格式**：
```markdown
## 修复记录

**审查报告**: <链接>

**修复**:
1. 测试缺失 → 补充边界测试（turn 15）
2. 命名不一致 → 统一为 `user_id`

**提交**:
- `abc123`: test: 添加密码为空边界测试
- `def456`: refactor: 统一 user_id 命名

**重新审查**: 准备提交给 @<审查者>
```

---

## 步骤⑤：通过

**审查者职责**：
- 确认严重问题已修复
- 宣布通过
- 更新 PLAN.md 状态

**输出格式**：
```markdown
## 审查通过

**任务**: <任务名称>

**审查者**: @<审查者>

**确认**:
- [x] 严重问题已修复
- [x] 一般问题已记录（HANDOFF.md）

**PLAN.md 状态**: 更新为 ✅ 完成

**时间**: 2026-10-16 20:00
```

---

## 审查频率

| 模式 | 频率 | 适用 |
|------|------|------|
| **每个任务审查** | 高频 | 重要功能，多 Agent 协作 |
| **每阶段审查** | 中频 | 单功能，阶段完成时 |
| **最终审查** | 低频 | 小功能，一次性审查 |

**推荐**：重要功能用**每个任务审查**，小功能可用**每阶段审查**。

---

## 与其他流程的衔接

- **自审** → 走 `tdd-playbook.md` 确认测试覆盖
- **发现架构问题** → 走 `architecture-review.md` 体检
- **修复复杂问题** → 走 `diagnosing-session.md` 诊断
- **更新 HANDOFF.md** → 走 `handoff.md` 格式
- **分支收尾** → 走 `finishing-branch.md`

---

## 常见错误

| 错误 | 症状 | 修复 |
|------|------|------|
| **攒到最后审查** | 问题堆积，修复成本高 | 强制每个任务审查 |
| **自审走过场** | 严重问题没发现 | 按清单逐项检查 |
| **审查不记录** | 问题修复无跟踪 | 审查报告落盘 |
| **修复不重新审查** | 可能引入新问题 | 修复后必须重新审查 |
| **一般问题忽略** | 技术债务堆积 | HANDOFF.md 记录排期 |

## 输出格式（完整报告）

```markdown
# 任务间审查报告

**任务**: <任务名称>

**日期**: 2026-10-16

---

## ① 自审

**自审结果**:
- [x] 功能符合 PLAN.md
- [x] 测试覆盖验收标准
- [x] 无硬编码
- [x] 无安全漏洞
- [x] 性能无回退
- [x] 命名符合 GLOSSARY.md

**已知问题**: 无

---

## ② 审查请求

**审查者**: @Agent-B

**变更**:
- `src/auth.py`（新增登录验证）
- `tests/test_auth.py`（新增测试）

**时间**: 20:00

---

## ③ 审查报告

**这个改动做了什么**: 给 `src/auth.py` 增加登录验证及配套测试

**Must fix**:
1. **密码为空时直接放行**（`src/auth.py:45`）
   - **这是什么**: 登录入口的空值分支
   - **问题**: 密码为空字符串时 `if not password` 判断顺序错误，返回了通过
   - **修法**: 把空值校验移到哈希比较之前
   - **不修的后果**: 空密码可登录，安全漏洞

**Should fix**:
2. **风险代码无失败测试**（`tests/test_auth.py`）——修复 1 后补一个"空密码必须拒绝"的红测试

**结论**: `Verdict: 先修 1。`

---

## ④ 修复

**修复提交**:
- `abc123`: test: 添加密码为空边界测试
- `def456`: refactor: 统一 user_id 命名

**重新审查**: 20:15

---

## ⑤ 通过

**确认**:
- [x] 严重问题已修复
- [x] 一般问题已记录（HANDOFF.md）

**PLAN.md 状态**: ✅ 完成

**审查者**: @Agent-B
```

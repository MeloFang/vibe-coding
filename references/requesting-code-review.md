# 任务间审查：每个任务完成后审查

> 触发说法："审查一下这个任务" / "检查实现质量" / "看看有没有问题" / "任务完成了，审查"

**铁律**：每个任务完成后**必须**走审查流程，**严重问题 blocking**（不许继续下一个任务）。

---

## 审查时机

```
任务完成 → 审查 → 修复（如有）→ 下一个任务
```

| 时机 | 说明 |
|------|------|
| **每个任务完成后** | 不许攒到最后一起审查 |
| **下一个任务开始前** | 确保问题不传递 |
| **严重问题 blocking** | 不许继续，先修复 |

---

## 审查检查清单

### 严重问题（blocking，必须修复）

- [ ] **功能不符合 PLAN.md / Dispatch 包**（做错了方向）
- [ ] **测试缺失**（没有测试或测试不覆盖验收标准）
- [ ] **硬编码**（配置/路径/密钥写死在代码里）
- [ ] **安全漏洞**（SQL 注入/XSS/路径遍历等）
- [ ] **性能回退**（关键路径性能下降>10%）
- [ ] **命名与 GLOSSARY.md 冲突**（术语不一致）

**处理**：发现任一 → **blocking**，必须修复后重新审查才能继续。

### 一般问题（non-blocking，可排期修复）

- [ ] **命名不一致**（同一概念用了不同名字）
- [ ] **代码重复**（DRY 违反，但不影响功能）
- [ ] **注释缺失**（复杂逻辑无注释）
- [ ] **格式问题**（缩进/空行/换行符）
- [ ] **提交信息不清晰**（commit message 模糊）

**处理**：记录到 HANDOFF.md，排期修复（不影响继续）。

---

## 审查流程

```
① 自审  →  ② 提交审查  →  ③ 审查者审查  →  ④ 修复（如有）→  ⑤ 通过
```

| 步骤 | 产物 | 出口条件 |
|:---|:---|:---|
| ① **自审** | 自审报告 | 作者已按清单检查 |
| ② **提交审查** | 审查请求 | 审查者已收到 |
| ③ **审查者审查** | 审查报告 | 严重问题已识别 |
| ④ **修复** | 修复提交 | 严重问题已修复 |
| ⑤ **通过** | 通过记录 | PLAN.md 状态更新 |

---

## 步骤①：自审

**作者职责**：在提交审查前，先自己按清单检查一遍。

**输出格式**：
```markdown
## 自审报告

**任务**: <任务名称>

**自审结果**:
- [x] 功能符合 PLAN.md / Dispatch 包
- [x] 测试覆盖验收标准
- [x] 无硬编码
- [x] 无安全漏洞
- [x] 性能无回退
- [x] 命名符合 GLOSSARY.md

**已知问题**:
- <如有一般问题，提前记录>

**提交审查**: 准备提交给 <审查者>
```

---

## 步骤②：提交审查

**提交方式**：
- 会话内：直接@审查者，粘贴审查请求
- 远端：GitHub PR / GitLab MR
- 本地：更新 PLAN.md 状态为"待审查"

**输出格式**：
```markdown
## 审查请求

**任务**: <任务名称>

**自审**: [x] 通过

**变更**:
- 文件 1: `src/auth.py`（新增登录验证）
- 文件 2: `tests/test_auth.py`（新增测试）

**审查者**: @<审查者>

**截止时间**: <可选，如"30 分钟内">
```

---

## 步骤③：审查者审查

**审查者职责**：
- 读代码 + 测试
- 按清单检查
- 输出审查报告

**输出格式**：
```markdown
## 审查报告

**任务**: <任务名称>

**审查者**: @<审查者>

**严重问题**:
- [ ] 无
- [x] 测试缺失（turn 12, line 45）
  - 缺少边界测试：密码为空的情况

**一般问题**:
- [x] 命名不一致
  - `user_id` vs `uid` 混用

**决定**: <继续/修复后继续/停止>

**理由**: <为什么>
```

---

## 步骤④：修复

**作者职责**：
- 逐条修复严重问题
- 更新提交
- 重新提交审查

**输出格式**：
```markdown
## 修复记录

**审查报告**: <链接>

**修复**:
1. 测试缺失 → 补充边界测试（turn 15）
2. 命名不一致 → 统一为 `user_id`

**提交**:
- `abc123`: test: 添加密码为空边界测试
- `def456`: refactor: 统一 user_id 命名

**重新审查**: 准备提交给 @<审查者>
```

---

## 步骤⑤：通过

**审查者职责**：
- 确认严重问题已修复
- 宣布通过
- 更新 PLAN.md 状态

**输出格式**：
```markdown
## 审查通过

**任务**: <任务名称>

**审查者**: @<审查者>

**确认**:
- [x] 严重问题已修复
- [x] 一般问题已记录（HANDOFF.md）

**PLAN.md 状态**: 更新为 ✅ 完成

**时间**: 2026-10-16 20:00
```

---

## 审查频率

| 模式 | 频率 | 适用 |
|------|------|------|
| **每个任务审查** | 高频 | 重要功能，多 Agent 协作 |
| **每阶段审查** | 中频 | 单功能，阶段完成时 |
| **最终审查** | 低频 | 小功能，一次性审查 |

**推荐**：重要功能用**每个任务审查**，小功能可用**每阶段审查**。

---

## 与其他流程的衔接

- **自审** → 走 `tdd-playbook.md` 确认测试覆盖
- **发现架构问题** → 走 `architecture-review.md` 体检
- **修复复杂问题** → 走 `diagnosing-session.md` 诊断
- **更新 HANDOFF.md** → 走 `handoff.md` 格式
- **分支收尾** → 走 `finishing-branch.md`

---

## 常见错误

| 错误 | 症状 | 修复 |
|------|------|------|
| **攒到最后审查** | 问题堆积，修复成本高 | 强制每个任务审查 |
| **自审走过场** | 严重问题没发现 | 按清单逐项检查 |
| **审查不记录** | 问题修复无跟踪 | 审查报告落盘 |
| **修复不重新审查** | 可能引入新问题 | 修复后必须重新审查 |
| **一般问题忽略** | 技术债务堆积 | HANDOFF.md 记录排期 |

> **注意**：审查不是"找茬"，是**确保质量不下降**。严重问题 blocking 不是"卡进度"，是"防止问题传递到下一个任务"。

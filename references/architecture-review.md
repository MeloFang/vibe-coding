# 代码库体检：找缺陷、架构摩擦与决策缺口

> 三类发现，一个都不能漏：**① 正确性缺陷（bug）② 架构摩擦（浅模块） ③ 决策缺口（悬空配置）**。
> 触发说法："体检架构 / 扫一下代码质量 / 找重构点 / 架构太乱 / 哪里该深挖 / 查查有没有 bug"。
> 深模块词汇表见 `deep-module-design.md`；本文件只讲流程。

---

## 铁律三条

1. **子 Agent 的发现是假设，不是事实。** 它只负责"看"，不负责"定"。凡影响正确性的，必须自己实证。
2. **体检阶段只读不写。** 不改代码、不提交、不推GitHub。发现问题只报告，改不改由用户拍板。
3. **判定"不是问题"的也要记录。** 否则下次体检会重复提同样的东西，白耗一轮。

---

## 阶段一：探索与取证

### 划范围（YAGNI）

体检的回报是"让改动更容易 + 别让bug 藏着"，所以**给最近改动过的部分加权**。

- 用户点名方向（模块 / 子系统 / 痛点）→ 直接用，跳过推断。
- 否则 → `git log --oneline` 翻一段提交历史，找**热点**：反复出现的文件和区域，让这些路径优先吸引注意力。改动分散就扩大范围。

先读 `GLOSSARY.md`（旧名 `CONTEXT.md`）和该区域 ADR——**不要重新推翻已有决策**。

### 派子 Agent 探索

不要套死板启发式，带着摩擦感去看。**三类都要看**：

**① 正确性缺陷**（优先级最高，最容易漏看）
- 顺序依赖：过滤 / 抑制 / 校验**跑在依赖它们的步骤之前**，导致注定要被淘汰的项提前杀掉了别人的合法输入
- 配置项声明了但**零个读取点**（→ 归入③类）
- 边界值处理：`max_len` / 长度上限的临界点前后行为不一致
- 名字与行为不符：变量名承诺了一件事，代码做了另一件
- 同一概念在多处重复实现（→ 归入②类）

**② 架构摩擦**
- 理解一个概念要在多少个小模块之间来回跳？
- 哪些模块是**浅的**——接口复杂度几乎等于实现复杂度？
- 哪些纯函数只为可测性抽出，但真正的 bug 藏在它们**怎么被调用**（缺 **locality**）？
- 哪些紧耦合模块跨接缝泄漏？
- 同一个概念是不是在多个地方各写一遍，还用了不同风格？

**③ 决策缺口**
- 配置 / 开关 / feature flag 声明了，但代码里**没有任何读取点** → 假承诺
- 变量名 / 契约与实际传值不符（比如声明了三个注入变量，实际调用方都传同一个）

对任何你怀疑是浅的模块做**删除测试**：想象删掉它，复杂度会**集中**还是只是**平移**？"集中"才是要的信号。

### 逐条实证（最关键的一步，不能省）

子 Agent 每条发现都必须带**证据等级**，并映射为**三级裁定**（借鉴 cloudflare/security-audit-skill）：

| 等级 | 裁定（verdict） | 含义 | 要求 |
|:---|:---|:---|:---|
| **✅ 已验证** | `confirmed` | 已经跑过、复现过、或代码路径已逐行核对确认 | 直接采信 |
| **⚠️ 需实测** | `needs_validation` | 逻辑上像有问题，但没实际跑过 | **必须自己动手测**，不能直接写进报告 |
| **💭 推断 / 证伪** | `rejected` | 直觉未验证 / 已被查证排除 | 进「已排除」区，记录否掉的理由 |

**影响正确性的发现，一律要实测复现。** 拿真实数据跑一遍，给出实测证据（输入 → 实际输出 → 期望输出）。不是推理，是复现。

> "没查清"（`needs_validation`）和"查清了是假的"（`rejected`）必须分开记录——前者是待办，后者是结论。混在一起下次体检还会重复劳动。

> 实测时顺手量化**触发频率**：在现有真实数据上跑，命中几次？0 次和 100 次是完全不同优先级。触发 0 次的 bug 优先级会显著下降——但**不是不修**，是"可以晚点修"。

## 阶段二：出HTML 报告 + findings.json

写**自包含HTML 到系统临时目录**（不要落进仓库），文件名 `architecture-review-<时间戳>.html`。写完为用户打开（Windows `start`；macOS `open`；Linux `xdg-open`），告知绝对路径。

### 同时产出机器可读 findings.json

HTML 给人看，**findings.json 给机器消费**（后续 CI、跨会话对比、自动化跟踪）。与 HTML 放同一临时目录，格式按 `report-schema.json`：

- `meta`：repo、时间戳、范围、`read_only: true`
- `findings[]`：每条带 `id`（全局连续）、`category`（correctness / architecture / decision_gap）、**`verdict`（confirmed / needs_validation / rejected）**、files（带行号）、problem（具体场景）、evidence（correctness+confirmed 必填）、fix（具体到改哪几处）、hit_count、recommendation、deferred
- `excluded[]`：判定"不是问题"的，每条带 `kind`（false_positive 误报 / intentional 刻意设计）

**写完必须过校验**（零依赖，标准库即可）：

```bash
python references/validate_report.py <findings.json>
```

校验不过（编号断档、confirmed 缺证据、修法含糊）→ 修数据再重跑，不许跳过。校验器自带测试：`python references/test_validate_report.py`（12 项断言，改 schema 时必须全绿）。

### 报告形式要求

- **Tailwind CDN** 做布局，**Mermaid CDN** 画图。
- 关系是图形的（调用图、依赖、时序）用 Mermaid；更编辑性的视觉（质量图、剖面图）用手工 div/SVG。**混合使用。**
- **每个候选都要有 before/after 对比图。**
- **三类发现分区展示**，不要混在一起——正确性缺陷要排在最前面。

### 候选卡片字段

| 字段 | 内容 |
|:---|:---|
| **类别** | 🔴 正确性缺陷 / 🟠 架构摩擦 / 🟡 决策缺口 |
| **证据等级** | ✅ 已验证 / ⚠️ 需实测 / 💭 推断 |
| **Files** | 涉及哪些文件 / 模块（带行号） |
| **Problem** | 问题是什么，为什么造成影响 |
| **实测证据** | 输入 → 实际输出 → 期望输出（**bug 类必填**） |
| **触发频率** | 在现有真实数据上命中几次 |
| **修法** | 具体到**改哪几处 / 换哪个顺序**，不是"应该重构" |
| **回归面** | 改完要重跑哪些东西 |
| **Benefits** | 用 **locality** / **leverage** 的语言说，以及测试会怎么变好 |
| **Before / After 图** | 并排自绘 |
| **推荐强度** | `Strong` / `Worth exploring` / `Speculative`，做成徽章 |

### 首推排序（不要按优雅度排）

按**性价比 × 风险**排，明确写下排序理由：

1. **正确性优先** —— 影响产品对错的排最前，不管修起来多小
2. **其次看修法成本** —— 改两行 vs 动两个模块，前者先做
3. **再次看 leverage** —— 收益大的靠后（因为改动大、风险高）
4. **YAGNI 兜底** —— 其余的**每条都要写清"触发条件"**（"等真做 X 时会自然撞上"），而不是笼统写"以后再说"

推荐理由里要带上这些实测信息（触发频率、修法大小、风险面），不要只讲架构收益。

### 判定为"不是问题"的，也要写进报告

单独开一区「**已排除**」，每条写清**为什么否**。这是体检最有复用的部分之一——避免下次重复论证。

需要实证否掉的，**去查一遍再说**（实战里子 Agent 提的"config 有两份缓存"就是查完发现 `load()` 返回同一个 dict 对象，前提根本不成立）。

> 注意两类不同：① **误报**（前提不成立，如"有副本"其实是别名）② **刻意设计**（如"集中点""为可测性留的注入点"）——刻意设计的要写明"该保留"，别让人后来当技术债清理掉。

### 用词纪律

- **领域概念**用 `GLOSSARY.md` 的说法：GLOSSARY 定义了 "Order" 就说"Order 受理模块"，别叫 `FooBarHandler`。
- **架构概念**用 `deep-module-design.md` 的词汇：module / interface / depth / seam / adapter / leverage / locality，**不漂移**成"组件、服务、API、边界"。

### ADR 冲突怎么标

候选与已有 ADR 矛盾时，**只有摩擦真实到值得重开 ADR** 才提，并明显标注（警告样式：*"与 ADR-0007 冲突，但值得重开，因为…"*）。别把 ADR 禁止的理论重构全列一遍——那是噪音。

### 这个阶段不要设计接口

写完文件后问用户："**想深入看哪一个？**"

## 阶段三：深挖对话

用户选定候选后，走烤问循环（见 `alignment-deep-dive.md`）：约束、依赖、深模块的形状、接缝背后放什么、哪些测试能活下来。

决策成型时**同步维护领域模型**：
- 深模块起的名字不在 `GLOSSARY.md` 里 → 加进去（文件不存在就懒创建）。
- 某模糊术语变清晰 → 当场更新 `GLOSSARY.md`。
- 用户以"承重理由"否决候选 → 提议写 ADR："要我记成 ADR 吗？免得以后体检又提一遍。"**只有这个理由是未来探索者确实需要知道时才提**；"现在不划算"这类临时理由、自明理由就别写。

## 报告之后：挂账与拍板

**体检结束 ≠ 要开工修。** 报告交付后要做三件事：

### 1. 需要修但用户选择暂缓的 → 写进项目记忆

不要只在对话里说"我记着了"，要**落进项目的 `HANDOFF.md` 或记忆文件**，下次会话才不会擅自开修。写法：

```
挂账：<问题一句话> —— <触发条件：什么时候值得修>
```

"触发条件"是关键：要么是"当前数据上触发 0 次，等真实数据出现再修"，要么是"等做 X 功能时会自然撞上"。有了触发条件，挂账才不会变成失踪的债。

### 2. 决策缺口类的 → 明确交给用户拍板

悬空配置（声明了但没接线）**不是 bug，是产品决策**——"这个开关你想不想有"。

- 想留这个能力 → 接上线（代码真正读它）
- 不需要 → 从配置里删掉，别留假承诺
- **悬空是唯一错误答案**

这类必须单独提出来问用户，**不能默默跳过也不能顺手改掉**。

### 3. 明确声明本次没动什么

报告收尾写清："本次体检只读，未修改代码 / 未提交 / 未推送。" 让用户知道边界在哪。

# vibe-coding

> 规划驱动 + 上下文固定 + AI 结对执行 —— 开项目就走固定流程，从立项一路到验证交付，全程有一份"程序是什么 + 到哪一步 + 怎么接手"的活文档。

一个跨项目通用的 AI 结对编程工作流技能。把「让 AI 写代码」从一次性碰运气，变成一条**可审计、可复盘、可移交**的流水线。

---

## 这个技能解决什么问题

AI 结对编程最常见的四种翻车方式：

| 失败模式 | 典型症状 | 本技能的约束 |
|:---|:---|:---|
| **做错方向** | 代码写完了，但不是你要的东西 | 开工前强制 **Grill 对齐**，先钉死目标 / 非目标 / 验收标准 |
| **术语混乱** | 20 个字解释 1 个字的 concepts，token 烧光 | `GLOSSARY.md` 固化**共享语言**，命名一致 |
| **代码不对** | 看着像那么回事，一跑就崩 | TDD **红→绿→重构** + 垂直切片 + 六阶段**诊断循环** |
| **架构泥球** | 越写越乱，改一处崩三处 | **深模块**设计词汇（module/interface/depth/seam）+ 代码库体检 |

更大的问题是**项目级**的：做着做着忘了要做什么、进度不明、接手的人看不懂。

- **目标漂移** → 强制先写 `PRODUCT.md`，成功标准可验证
- **进度不明** → `PLAN.md` 状态机 + `HANDOFF.md` 阶段进度表
- **接手看不懂** → `HANDOFF.md` 讲清"这程序是什么 / 到哪一步 / 怎么接手"
- **藏着 bug** → 代码库体检覆盖三类发现：**正确性缺陷 / 架构摩擦 / 决策缺口**，且**子 Agent 的发现必须自己实证**才算数

## 核心：项目全生命周期

**开新项目时走这条固定流程**：

```
① 立项与产品文档→  ② 固定上下文  →  ③ 规划  →  ④ 实现  →  ⑤ 验证
     PRODUCT.md        AGENTS.md      PLAN.md     代码+测试   验收
                       GLOSSARY.md
                       docs/adr/
                       └── ⑥ 续接文档 HANDOFF.md（全程维护，每个阶段都更新）
```

| 阶段 | 产物 | 出口条件 |
|:---|:---|:---|
| ① **立项与产品文档** | `PRODUCT.md` | 成功标准可验证 + **用户确认**（未确认不许进下一阶段） |
| ② **固定上下文** | `AGENTS.md` + `GLOSSARY.md` + `docs/adr/` | 新 Agent 读完就能开工，不用问基础问题 |
| ③ **规划** | `PLAN.md` | 每步带验收信号，粒度一天左右，只写指令不写实现 |
| ④ **实现** | 代码 + 测试 | 红→绿走完，状态已更新 |
| ⑤ **验证** | 验收记录 | 对着成功标准逐条核对，**人来下结论** |
| ⑥ **续接文档** | `HANDOFF.md` | **从①就建，每阶段更新** |

**规模适配**：一次性脚本走 ②③④；单个功能走 ②③④⑤ + 简版 HANDOFF；完整项目走全六阶段。

判断标准：**会不会跨越会话？会不会有别人接手？** 会 → 走全流程。但**产品文档永远值得写**，哪怕三行字。

### 7 项核心优化（来自 Superpowers 方法论）

本技能融合了 7 项来自 `obra/superpowers` 的核心优化，覆盖项目全生命周期：

| 优化 | 作用 | 对应 reference |
|:---|:---|:---|
| **① 会话诊断** | 当会话出问题时，4 阶段流程定位根因（建环→复现→假设→修复） | `diagnosing-session.md` ★ P0 |
| **② 分支收尾** | 功能完成后标准化收尾（验证→清理→合并→复盘） | `finishing-branch.md` ★ P0 |
| **③ 子 Agent 并行** | 拆任务→分配→协调→合并，提升开发效率 | `subagent-driven-development.md` ★ P1 |
| **④ Git Worktree 隔离** | 多分支并行开发，互不干扰 | `using-git-worktrees.md` ★ P1 |
| **⑤ 任务间审查** | 每个任务完成后对照清单审查，防缺陷累积 | `requesting-code-review.md` ★ P2 |
| **⑥ 接收审查反馈** | 如何高效响应审查意见，不玻璃心 | `receiving-code-review.md` ★ P2 |
| **⑦ TDD 强制机制** | TDD 不是建议，是强制执行的开发流程 | `tdd-playbook.md` ★ P0 |

> **优先级说明**：P0 = 必须掌握；P1 = 推荐掌握；P2 = 进阶优化

## 新项目会出现什么

> 结论前置：一个新项目会"出现"两层东西——**一定会落盘的骨架文档**（看得见的文件）和**过程中按情境触发的纪律流程**（看不见，但决定代码对不对）。

### 开工第一天，目录长这样

```
my-project/
├── PRODUCT.md        # ① 决策锚点：解决什么问题 + 成功标准 + 明确不做
├── AGENTS.md         # ② 怎么构建、怎么测、代码什么风格
├── GLOSSARY.md       # ② 这个项目的黑话分别指什么
├── PLAN.md           # ③ 拆成几步，每步怎么算做完
├── HANDOFF.md        # ⑥ 活文档：是什么 / 到哪了 / 怎么接
├── docs/
│   └── adr/          # ② 决策记录（不是什么都记，见下）
│       └── 0001-xxx.md
└── src/ + tests/     # ④ 红→绿→重构的产物
```

**最容易搞错的一点**：`HANDOFF.md` 不是最后才补的交付说明，是**从立项第一天就建、每个阶段都更新**的活文档。当成"收尾时补一份介绍"就废了。

### 过程中会额外触发什么

| 什么时候 | 会出现什么 | 具体动作 |
|:---|:---|:---|
| **进入实现前** | GitHub 查重 | 先按 `references/github-scouting.md` 搜现成开源，能抄不写 |
| **写代码时** | TDD 红 → 绿 → 重构 | 先写失败测试再写实现，**强制流程不是建议** |
| **卡住 / 出 bug** | 会话诊断 | 建环 → 复现最小化 → 假设 → 插桩 → 修复 → 回归 |
| **一个功能做完** | 分支收尾 | 验证 → 清理调试代码 → 合并 → 复盘，**不许直接开下一个** |
| **每个任务完成** | 代码审查 | 对照清单过一遍，防缺陷攒到最后爆雷 |
| **收到审查意见** | 反馈响应 | 先判断对不对再改，不玻璃心也不盲从 |
| **多任务要并行** | 子 Agent + Git Worktree | 拆任务分发，各占一条分支互不干扰 |

### 按规模，出现的东西不一样

判定标准：**会不会跨越会话？会不会有别人接手？**

| 规模 | 走哪些阶段 | 实际会出现 |
|:---|:---|:---|
| **一次性脚本 / 小工具**（<半天） | ②③④，①口头确认 | 代码 + 测试，几乎不留文档 |
| **单个功能**（1–3 天） | ②③④⑤ + 简版 HANDOFF | AGENTS + PLAN + 进度，不写 ADR |
| **完整项目**（>1 周） | 全六阶段 | PRODUCT + AGENTS + GLOSSARY + ADR + PLAN + HANDOFF 全套 |

> 但**产品文档（①）永远值得写**，哪怕三行字。它是"为什么要做这件事"的唯一记录。

### 几条反直觉的硬规矩

1. **产品定义必须你来拍板** —— Agent 只起草，不许自己定义产品。
2. **验收必须人下结论** —— Agent 可以跑测试，但不能自己宣布"验收通过"。
3. **ADR 不是什么都记** —— 只有"难以逆转 + 无上下文会困惑 + 源于真实权衡"三条全中才写。
4. **规划只写指令不写实现** —— `PLAN.md` 里不该出现大段代码。
5. **代码库体检时，子 Agent 的发现必须自己实证** —— 发现是假设，验证过才算数。
6. **临时会话交接不落仓库** —— 跨 Agent 接力的单次交接写系统临时目录，别污染 `HANDOFF.md`。

## 续接文档：讲清三件事

`HANDOFF.md` 是给"完全不了解这个项目的人"看的，**从立项第一天就建，每阶段更新**：

1. **这个程序是什么** —— 一句话定义、背景、怎么工作（含流程图）、用户怎么用、技术概览
2. **做到哪一步** —— 阶段进度表、已完成功能、进行中（带卡点）、还没做、已知问题
3. **怎么接着做** —— 下一步具体动作、从哪里开始读、环境准备命令、注意事项

> **临时交接 vs 长期文档**：`HANDOFF.md` 是项目级活文档（讲程序和进度）；跨 Agent 接力的单次会话交接写进系统临时目录，不落仓库。

## 五步闭环（单个功能的编码内核）

每个编码任务都走完，**不跳步，不一上来就写代码**：

```
① 对齐 Grill  →  ② 固定上下文  →  ③ 规划  →  ④ 分步实现  →  ⑤ 复盘
   ↓↓            ↓              ↓           ↓            ↓
问清要做什么    写进 AGENTS.md   小步带验收   一次改一块    验证 + 更新上下文
不做什么        GLOSSARY.md     只写指令     跑验证        可复盘提交
```

### ① 对齐（Grill）

最贵的失败不是写错代码，是**做错方向**：

- **目标**是什么？**非目标**（明确不做）是什么？
- 技术栈 / 约束 / 已有代码在哪？
- **验收标准**是什么（怎么算"做对了"）？
- 风险点 / 不确定项？

轻量任务用这四行。**复杂需求别只问一轮**——按"设计树 + 前沿"多轮追问，见 `alignment-deep-dive.md`。

### ② 固定上下文

把结论**写进文件**，让每轮有据可依，不靠聊天记忆：

| 文件 | 作用 |
|:---|:---|
| `AGENTS.md` | 单一文件三段式（AGENTS / CLAUDE / GEMINI），一份喂所有编码 Agent |
| `GLOSSARY.md` | 项目专属领域词汇与共享语言（+ ADR 记录决策） |
| `PLAN.md` | 分步计划，每步带验收信号 |

### ③ 规划

**先按 `references/github-scouting.md` 在 GitHub 查重（能抄不写）**——动手前确认有没有现成开源可复用。然后再拆成小步，每步带明确验收。规划阶段**只写指令，不写实现**。

### ④ 分步实现

**一次只改一个模块 / 一步**，改完跑验证。代码一多就切会话（新会话先读上下文文件）。

### ⑤ 复盘

验证通过再继续；更新上下文与进度；提交要可复盘。

## 两条铁律

### 反馈环铁律（TDD 强制机制）

- **红在前**：先写失败测试，再写最少代码让它绿。不预支未来测试。
- **只在预先约定的接缝上测**：写测试前先跟用户确认要测哪些接缝。
- **期望值必须来自独立真相源**：不能用代码同样的算法算期望值。
- **垂直切片，不要水平**：一个测试 → 一个实现 → 重复。
- **诊断先建环**：硬 bug 第一步是造一个"能红、确定、秒级"的反馈环。
- **强制执行**：TDD 不是建议，是强制流程。每个任务必须先写测试（红），再写实现（绿），最后重构。见 `tdd-playbook.md` 强制机制。

### 一次一片

一个边界、一个测试、一次最小实现。别一次铺开。

## 心法：道法术器

| 层次 | 内容 |
|:---|:---|
| **道**（原则） | 规划就是一切；上下文是第一性（垃圾进垃圾出）；奥卡姆剃刀；帕累托；逆向思考；先结构后代码 |
| **法**（方法） | 一句话目标 + 非目标；能抄不写（先问有没有现成库）；接口先行、实现后补；一次只改一个模块；文档即上下文 |
| **术**（技巧） | 明确「能改什么 / 不能改什么」；Debug 只给「预期 vs 实际 + 最小复现」；测试交给 AI 但断言人审；代码一多就切会话 |
| **器**（工具） | 复杂任务选第一梯队模型；CLI 型 Agent 优先（Claude Code / Codex / Cursor等）；tmux 多会话；本地模型做敏感数据 |

## 怎么用

### 自动触发

对话里说下面任意一句，技能会被自动加载：

> 开个新项目 / 从零做一个东西 / 我要立项 / 走完整流程 / 生成产品文档 / **做到哪一步了** / 按 vibe coding 来 / 先对齐 / 烤问 / grill / 跑 TDD / 写测试 / 诊断这个 bug / 固定上下文 / 体检架构 / 扫代码质量 / **查查有没有 bug** / 交接给下个会话 / 换人接着做

### 主动指定

> 用 vibe coding 帮我开个新项目，做一个 XXX

### 典型对话

```
你：用 vibe coding 帮我开个新项目，做个批量重命名工具
我：（① 立项）起草 PRODUCT.md，你审改确认成功标准和范围边界
    （② 上下文）建 AGENTS.md + GLOSSARY.md
    （③ 规划）拆成 4 步，每步带验收信号，写进 PLAN.md
    （④ 实现）建 HANDOFF.md 持续更新；先写失败测试（红），再写最少实现（绿）
    （⑤ 验证）对着成功标准逐条核对，你来下结论
    （⑥ 交接）HANDOFF.md 更新进度，下一个人从这儿接

你：这个 bug 有点怪，诊断一下
我：（会话诊断）① 建立反馈环 → ② 最小化复现 → ③ 提出假设 → ④ 插桩验证 → ⑤ 修复 → ⑥ 回归
    全程子 Agent 发现必须自己实证，不甩锅

你：功能做完了，怎么收尾
我：（分支收尾）① 验证验收标准 → ② 清理调试代码 → ③ 合并到主分支 → ④ 复盘更新上下文

你：用子 Agent 并行实现这几个功能
我：（子 Agent 开发）① 拆成独立任务 → ② 分配给不同子 Agent → ③ 协调进度 → ④ 合并代码

你：这个任务完成后审查一下
我：（任务间审查）对照审查清单逐项检查 → 生成审查报告 → 更新 PLAN.md 状态
```

## 写子技能

想把某条纪律固化成独立技能，照 `references/SKILL-spec.md` 来。核心要求：

- 目录名与 frontmatter 的 `name` 一致（kebab-case）
- **`description` 就是触发词**，写清「什么时候用」，否则不会被正确加载
- 正文是自包含的纪律参考：分阶段 / 分节，每节可独立查阅
- 长的示例放 `references/`，正文只链不堆

> **优先留在 `references/` 里**：拆出去的技能会独立成目录，随「该触发时没触发」的风险。除非某条纪律自成一体且触发场景明显不同，否则留在本技能内。

# vibe-coding

> 规划驱动 + 上下文固定 + AI 结对执行 —— 开项目就走固定流程，从立项一路到验证交付，全程有一份"程序是什么 + 到哪一步 + 怎么接手"的活文档。

一个跨项目通用的 AI 结对编程工作流技能。把「让 AI 写代码」从一次性碰运气，变成一条**可审计、可复盘、可移交**的流水线。

---

## 这个技能解决什么问题

AI 结对编程最常见的四种翻车方式：

| 失败模式 | 典型症状 | 本技能的约束 |
|:---|:---|:---|
| **做错方向** | 代码写完了，但不是你要的东西 | 开工前强制 **Grill 对齐**，先钉死目标 / 非目标 / 验收标准 |
| **术语混乱** | 20 个字解释1 个字的 concepts，token 烧光 | `GLOSSARY.md` 固化**共享语言**，命名一致 |
| **代码不对** | 看着像那么回事，一跑就崩 | TDD **红→绿→重构** + 垂直切片 + 六阶段**诊断循环** |
| **架构泥球** | 越写越乱，改一处崩三处 | **深模块**设计词汇（module/interface/depth/seam）+ 代码库体检 |

更大的问题是**项目级**的：做着做着忘了要做什么、进度不明、接手的人看不懂。

- **目标漂移** → 强制先写 `PRODUCT.md`，成功标准可验证
- **进度不明** → `PLAN.md` 状态机 + `HANDOFF.md` 阶段进度表
- **接手看不懂** → `HANDOFF.md` 讲清"这程序是什么 / 到哪一步 / 怎么接手"
- **藏着 bug** → 代码库体检覆盖三类发现：**正确性缺陷 / 架构摩擦 / 决策缺口**，且**子 Agent 的发现必须自己实证**才算数

## 核心：项目全生命周期

**开新项目时走这条固定流程**：

```
① 立项与产品文档→  ② 固定上下文  →  ③ 规划  →  ④ 实现  →  ⑤ 验证
     PRODUCT.md        AGENTS.md      PLAN.md     代码+测试   验收
                       GLOSSARY.md
                       docs/adr/
                       └── ⑥ 续接文档 HANDOFF.md（全程维护，每个阶段都更新）
```

| 阶段 | 产物 | 出口条件 |
|:---|:---|:---|
| ① **立项与产品文档** | `PRODUCT.md` | 成功标准可验证 + **用户确认**（未确认不许进下一阶段） |
| ② **固定上下文** | `AGENTS.md` + `GLOSSARY.md` + `docs/adr/` | 新 Agent 读完就能开工，不用问基础问题 |
| ③ **规划** | `PLAN.md` | 每步带验收信号，粒度一天左右，只写指令不写实现 |
| ④ **实现** | 代码 + 测试 | 红→绿走完，状态已更新 |
| ⑤ **验证** | 验收记录 | 对着成功标准逐条核对，**人来下结论** |
| ⑥ **续接文档** | `HANDOFF.md` | **从①就建，每阶段更新** |

**规模适配**：一次性脚本走 ②③④；单个功能走 ②③④⑤ + 简版 HANDOFF；完整项目走全六阶段。

判断标准：**会不会跨越会话？会不会有别人接手？** 会 → 走全流程。但**产品文档永远值得写**，哪怕三行字。

## 续接文档：讲清三件事

`HANDOFF.md` 是给"完全不了解这个项目的人"看的，**从立项第一天就建，每阶段更新**：

1. **这个程序是什么** —— 一句话定义、背景、怎么工作（含流程图）、用户怎么用、技术概览
2. **做到哪一步** —— 阶段进度表、已完成功能、进行中（带卡点）、还没做、已知问题
3. **怎么接着做** —— 下一步具体动作、从哪里开始读、环境准备命令、注意事项

> **临时交接 vs 长期文档**：`HANDOFF.md` 是项目级活文档（讲程序和进度）；跨 Agent 接力的单次会话交接写进系统临时目录，不落仓库。

## 五步闭环（单个功能的编码内核）

每个编码任务都走完，**不跳步，不一上来就写代码**：

```
① 对齐 Grill  →  ② 固定上下文  →  ③ 规划  →  ④ 分步实现  →  ⑤ 复盘
   ↓↓            ↓              ↓           ↓            ↓
问清要做什么    写进 AGENTS.md   小步带验收   一次改一块    验证 + 更新上下文
不做什么        GLOSSARY.md     只写指令     跑验证        可复盘提交
```

### ① 对齐（Grill）

最贵的失败不是写错代码，是**做错方向**：

- **目标**是什么？**非目标**（明确不做）是什么？
- 技术栈 / 约束 / 已有代码在哪？
- **验收标准**是什么（怎么算"做对了"）？
- 风险点 / 不确定项？

轻量任务用这四行。**复杂需求别只问一轮**——按"设计树 + 前沿"多轮追问，见 `alignment-deep-dive.md`。

### ② 固定上下文

把结论**写进文件**，让每轮有据可依，不靠聊天记忆：

| 文件 | 作用 |
|:---|:---|
| `AGENTS.md` | 单一文件三段式（AGENTS / CLAUDE / GEMINI），一份喂所有编码 Agent |
| `GLOSSARY.md` | 项目专属领域词汇与共享语言（+ ADR 记录决策） |
| `PLAN.md` | 分步计划，每步带验收信号 |

### ③ 规划

拆成小步，每步带明确验收。规划阶段**只写指令，不写实现**。

### ④ 分步实现

**一次只改一个模块 / 一步**，改完跑验证。代码一多就切会话（新会话先读上下文文件）。

### ⑤ 复盘

验证通过再继续；更新上下文与进度；提交要可复盘。

## 两条铁律

### 反馈环铁律

- **红在前**：先写失败测试，再写最少代码让它绿。不预支未来测试。
- **只在预先约定的接缝上测**：写测试前先跟用户确认要测哪些接缝。
- **期望值必须来自独立真相源**：不能用代码同样的算法算期望值。
- **垂直切片，不要水平**：一个测试 → 一个实现 → 重复。
- **诊断先建环**：硬bug 第一步是造一个"能红、确定、秒级"的反馈环。

### 一次一片

一个边界、一个测试、一次最小实现。别一次铺开。

## 心法：道法术器

| 层次 | 内容 |
|:---|:---|
| **道**（原则） | 规划就是一切；上下文是第一性（垃圾进垃圾出）；奥卡姆剃刀；帕累托；逆向思考；先结构后代码 |
| **法**（方法） | 一句话目标 + 非目标；能抄不写（先问有没有现成库）；接口先行、实现后补；一次只改一个模块；文档即上下文 |
| **术**（技巧） | 明确「能改什么 / 不能改什么」；Debug 只给「预期 vs 实际 + 最小复现」；测试交给 AI 但断言人审；代码一多就切会话 |
| **器**（工具） | 复杂任务选第一梯队模型；CLI 型 Agent 优先（Claude Code / Codex / Cursor等）；tmux 多会话；本地模型做敏感数据 |

## 安装

用户级安装，所有项目自动可用。

### WorkBuddy

```bash
git clone <this-repo> ~/.workbuddy/skills/vibe-coding
```

或直接把 `vibe-coding/` 整个目录拷到 `~/.workbuddy/skills/` 下。

### 其他 Agent（通用）

技能就是一个文件夹 + 一个 `SKILL.md`，把 `vibe-coding/` 放进目标 Agent 的技能目录即可：

- Claude Code → `.claude/skills/vibe-coding/`
- Codex / Cursor / OpenCode → 对应的 skills 目录

```

├── README.md                        # 本文件
└── references/
    ├── project-lifecycle.md         # ★ 项目全生命周期（六阶段 + 规模适配）
    ├── project-docs.md              # ★ 产品文档 / 实施计划 / 续接文档三份模板
    ├── repo-setup-and-tasks.md      # 仓库初始化清单 + 任务状态机
    ├── alignment-deep-dive.md       # 对齐深挖：设计树 + 前沿多轮追问
    ├── tdd-playbook.md              # TDD：好测试、接缝、三个反模式、循环规则
    ├── deep-module-design.md        # 深模块词汇：module/interface/depth/seam/adapter
    ├── architecture-review.md# 代码库体检：bug / 浅模块 / 决策缺口三类发现 → HTML 报告

    ├── CONTEXT-template.md          # 共享语言 / 术语表模板
    └── SKILL-spec.md                # 如何写自己的新技能
```

## 怎么用

### 自动触发

对话里说下面任意一句，技能会被自动加载：

> 开个新项目 / 从零做一个东西 / 我要立项 / 走完整流程 / 生成产品文档 / **做到哪一步了** / 按 vibe coding 来 / 先对齐 / 烤问 / grill / 跑 TDD / 写测试 / 诊断这个 bug / 固定上下文 / 体检架构 / 扫代码质量 / **查查有没有 bug** / 交接给下个会话 / 换人接着做

### 主动指定

> 用 vibe coding 帮我开个新项目，做一个 XXX

### 典型对话

```
你：用 vibe coding 帮我开个新项目，做个批量重命名工具
我：（① 立项）起草 PRODUCT.md，你审改确认成功标准和范围边界
    （② 上下文）建 AGENTS.md + GLOSSARY.md
    （③ 规划）拆成 4 步，每步带验收信号，写进 PLAN.md
    （④ 实现）建 HANDOFF.md 持续更新；先写失败测试（红），再写最少实现（绿）
    （⑤ 验证）对着成功标准逐条核对，你来下结论
    （⑥ 交接）HANDOFF.md 更新进度，下一个人从这儿接
```

## 写子技能

想把某条纪律固化成独立技能，照 `references/SKILL-spec.md` 来。核心要求：

- 目录名与 frontmatter 的 `name` 一致（kebab-case）
- **`description` 就是触发词**，写清「什么时候用」，否则不会被正确加载
- 正文是自包含的纪律参考：分阶段 / 分节，每节可独立查阅
- 长的示例放 `references/`，正文只链不堆

> **优先留在 `references/` 里**：拆出去的技能会独立成目录，随「该触发时没触发」的风险。除非某条纪律自成一体且触发场景明显不同，否则留在本技能内。
